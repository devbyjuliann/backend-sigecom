FALLOS PARCIALES Y PROPIEDAD ANTES DEL INCREMENTO 1D
(HISTÓRICO; EL REGISTRO LOCAL DURABLE SE DESCRIBE EN LA SECCIÓN INCREMENTO 1D)

El DDL de aprovisionamiento no es atómico y no existe limpieza automática:

- CREATE DATABASE: si hay error o se pierde la respuesta, el esquema puede
  existir aunque `resources.retained.schema` no quede marcado.
- CREATE USER APP/MIGRATOR: los objetos creados antes del fallo se conservan;
  una respuesta perdida puede volver incierta la marca `retained`.
- GRANT: puede quedar aplicado sólo uno de los dos grants. El objeto de usuario
  sí se registra como retenido, pero no hay marcas por grant.
- CREATE TABLE schema_migrations o aplicación de migraciones: DDL puede
  persistir aunque falle el registro de versión. `appliedMigrations` sólo agrega
  una versión tras insertar su fila, por lo que no prueba ausencia de DDL parcial.
- Fixtures: las filas insertadas antes de un fallo quedan retenidas.
- Registro de propiedad: no existe un registro duradero separado. El proceso
  imprime RUN_ID, esquema, nombres derivados y marcas de recursos al cerrar
  normalmente; un corte forzado puede impedir ese resumen. No marcar una
  ejecución como limpia a partir de la ausencia del resumen.

El fallo de aprovisionamiento inicial se reduce a operación/código SQL y el
`finally` cierra la conexión administrativa; el dispatcher devuelve el fallo y
no reintenta ni cambia RUN_ID. Los recursos se conservan. Ante un error:
detenerse, preservar el mismo RUN_ID/ATTEMPT_ID y el diagnóstico emitido, hacer
reconciliación exacta de metadatos y solicitar autorización independiente que
enumere recursos y reparación permitida. No volver a ejecutar PROVISION ni
iniciar otro RUN_ID para eludir el estado parcial.
